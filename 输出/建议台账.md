# 建议台账

> **这个文件存在的唯一目的：让"建议"有地方去，从而不必立刻做掉。**
>
> 过去两周的病根之一是：审查意见散落进各轮验收记录，变成 60 多条新禁令，
> 每一条都在下一轮变成必须完成的任务，于是每轮范围都在膨胀，永远收不了口。
>
> 规则：
> 1. 非阻塞的审查意见**只能写进本文件**，不得写进验收记录、阶段说明或脚本注释。
> 2. 每条必须有**归属阶段**。没到那个阶段就不做，做了也不算本轮成果。
> 3. 本文件不是合同。它不产生约束力，只是备忘。
>    真正的约束只在《唯一尺寸与画风合同》里，且改动需用户同意。
> 4. 一条建议被采纳落地后，划掉并注明在哪一轮做的。

### S-01　自检与调色仍依赖遗留美术常量
- **来源**：Codex review B0/B1（2026-08-24），第 2 条，非阻塞
- **现象**：
  - `?selftest` 的宽度检查与头像差异检查仍直接读 `BODY / AVATAR / AVATAR_BREATH / HEAD_SIDE / HEAD_DOWN`
  - `drawSwimmers` 对正式帧也会先调用 `colorsFor()`（读 `AVATAR_PAL`），结果随后被 `f.pal` 覆盖，属无用功
- **影响**：不影响换美术，两版 selftest 均 PASS。但只要这些引用还在，遗留美术常量就删不掉。
- **归属阶段**：**A3**（全部 32 个动作有正式帧、占位清零时），届时连同遗留常量一并删除
- **不要提前做的理由**：占位帧现在仍是唯一能覆盖 KICK/GRAPPLE/MOUNT 等动作的资产，
  B2/B3 还要靠它们；提前删会让 B2 无帧可用。

### S-02　时间到判负时，败者不进入 LOSE 状态
- **来源**：Codex review B0/B1（2026-08-24），第 4 条，非阻塞
- **现象**：`endMatch()` 只把 `hpFp <= 0` 的角色设为 `ST.LOSE`。
  时间到按 HP 判负时，HP 未归零的败者会冻结在当前状态（可能是 UW、JUMP 等）。
- **影响**：不影响胜负规则，只影响结算画面的观感。
- **归属阶段**：**B4**（气绝 / 败北 / 结算）——败北演出本来就是该阶段的内容

### S-03　`.bak` 不是历史恢复点
- **来源**：Codex review B0/B1（2026-08-24），第 6 条，非阻塞
- **现象**：`bake.py` 的 `--inject` / `--restore-placeholder` 对**主 HTML 内容**是幂等的，
  但每次都会用当前 HTML 覆盖 `.html.bak`。连续两次操作后，第一次的备份就没了。
- **影响**：只要不把 `.bak` 当版本历史用就没有问题。真正的历史在 git 里。
- **归属阶段**：**随手**——下一次有人改 `bake.py` 时，在文件头注释里写明这一点即可。
  不值得为它单独开一轮。

### S-04　正式帧上的判定盒是锚点相对的外推值
- **来源**：Kimi B2（2026-08-24），自记，非阻塞
- **现象**：hitbox/hurtbox 表现在统一由 `attachBoxes()` 注入，数据按占位帧几何（38px 横卧等）
  以锚点相对坐标写成。本地美术版的正式帧更宽（UW 59–61px），盒子能用且两版自检均 PASS，
  但覆盖率是按占位几何外推的，不是按正式帧实测的。
- **实测（2026-08-25 复核，补充具体数字）**：盒子尺寸不随帧宽变化，两版覆盖率差一倍——

  | 帧 | 占位帧宽 → 覆盖率 | 正式帧宽 → 覆盖率 |
  |---|---|---|
  | `yy.UW.R.0` | 38px → 95% | 59px → 61% |
  | `yy.SURF.R.0` | 24px → 83% | 61px → 33% |
  | `dd.UW.R.0` | 38px → 95% | 61px → 59% |

  即：同一套玩法数值，在正式美术下"打不中"的判定范围明显更大（尤其 SURF）。
  这不是 bug——盒子本来就该只包住躯干、不含伸展的手臂——但**当前值是按占位几何猜的，
  没有按正式帧量过**，所以两版的手感必然不同。
- **归属阶段**：**A3**（正式帧补齐时），按正式帧逐动作复核一遍盒子
- **不要提前做的理由**：正式帧只有 8 张、还在变，现在按它写死盒子会反复返工。

### S-06　正式帧上左右朝向的判定盒差 1px（占位帧不受影响）
- **来源**：2026-08-25 复核实测，非阻塞
- **现象**：`attachBoxes()` 的镜像式子是 `x = f.w - f.anchorX - rx - w`。
  这个式子只有在 `anchorX == f.w / 2` 时才等价于"关于锚点镜像"。
  - 占位帧的 `anchorX` 全部恰好等于 `w/2` → **164 帧中 0 帧不对称**。
  - 正式帧的 `anchorX` 来自 `bake.py` 的 `cx`，奇数宽时不等于 `w/2`
    → **164 帧中 74 帧左右差 1px**（全部差值都是 +1，如 `yy.SURF`：右 -10 / 左 -9）。
- **影响**：朝左和朝右的判定范围差 1 像素。确定性不受影响（差值是固定的，不是随机的），
  两版 selftest 均 PASS，不崩。属于手感层面的细微不对称。
- **归属阶段**：**A3**，与 S-04 一起复核（同一个函数、同一批数据，一次改完）
- **修法备忘**：改成按锚点镜像 `x = f.anchorX - rx - w`，或在 `bake.py` 里把 `cx` 统一取到
  `w/2`。两者选一即可，不要两处都改。

### S-07　肩组一旦抓住，被抓的一方没有活路
- **落地于**：B3a-fix（2026-08-25），用户拍板
- **做法**：采用"连打挣脱"方向。肩组建立时定死角色（主动方 attacker / 被抓方 defender）：
  主动方按 B = 出拳；被抓方的 A/B 连打边沿累积挣脱值（`escapePerPressFp`/`escapeMaxFp`，估值 1/12），
  攒满强制 `GRAPPLE_OFF`。挣脱值只由被抓方自己的输入累积，攻击方出拳不影响。
  原有无输入超时（`grappleIdleTicks`）与纠缠上限（`grappleMaxTicks`）保留为兜底路径。
- **verify.js 实测**：攻防同时连打 → 被抓方 1.1 秒挣脱（余 HP 36/48）；
  被抓方不动 → 4.5 秒被打死。「被抓方的活路」阻塞项两版均转绿。

### S-05　interaction 的 pairAnchor / facing / drawOrder 语义待肩组复核
- **落地于**：B3a（2026-08-25）
- **结论**：语义已定稿并写进主 HTML 的 interaction 块注释——
  `pairAnchor`：KICK=双方锚点中点（仅信息）；GRAPPLE=共用接触锚点，建立时定格，双方每 tick 钉位；
  `facing`：KICK=攻击方朝向；GRAPPLE=aId→bId 的纠缠朝向（决定钉位左右）；
  `drawOrder`：防守方/被揍方先画，攻击方/出拳方叠上层，肩组对峙时发起方在上。
  `GRAPPLE_PUNCH` 的 hitbox 已按相位启用（出拳命中扣血实测通过）。
