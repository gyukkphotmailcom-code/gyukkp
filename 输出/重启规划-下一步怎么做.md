## 一、先说结论：你没有偏，你是被流程锁住了

三个事实，都可以在仓库里查证：

**1. 游戏本体已经 6 天、11 轮没有改动过一个字节。**

`阳阳水泳大乱斗-原版复刻.html` 最后一次真实修改是 08-18 02:12。此后所有工作产出了
3184 行验收文档、8 个生成器脚本、72 张人物稿——**进入游戏的是 0 张**。
更关键的是，"主 HTML 的 SHA 没有变化"在 17 轮里有 11 轮被写成**通过条件**。
也就是说，每一轮都必须先证明自己没碰那个唯一能被你玩到的东西，才有资格 PASS。
不动交付物被制度化成了验收标准。

**2. 真正卡住项目的不是美术，是玩法根本没开始做。**

规格书第 12 节有 42 条验收项，现在可以勾上约 13 条。已经做得相当扎实的是：
静态场景、HUD 框架、单人移动内核（跳跃/下潜/八向/加速/超级换气/耗氧、60Hz 定点、确定性）。

**完全没有一行代码的是**：HP、比赛倒计时、胜负判定、踢击、肩组、肩组出拳、拉脚、
骑头、气绝掉血、败北演出、结算画面、爸爸 AI、2P、触屏、音频、池底奖牌、赛前道具。

第 1023 行写着 `tickChar(dad, IDLE_INPUT)`——爸爸至今是个接收空输入的木偶。
HUD 里的 HP 条是 `fillRect(40,191,60,7)` 画死的满槽，TIME 是硬编码的字符串 `'3:00'`。

**这里面有一半以上完全不依赖人物美术，现在就能开工。**

**3. 人物画不像，不是画得不够努力，是那条能传递"像"的通道被规则亲手切断了。**

所有 CONCEPT-* 生成器都在文件头写着同一句话：

> "两张本地概念参考图仅供人工观察，不作为构建输入。"
> —— `build_concept_1a.py:6`、`build_concept_model_0.py:6`、`CONCEPT-1A构建复现记录.md:7`

于是链路变成了：

```
真人照片 → AI 生成概念图（第一次有损）
        → 人眼看图写成中文形容词（第二次有损，且比例信息在这一步全部丢失）
        → 模型把形容词翻译成 rect/ellipse/polygon 的整数坐标（第三次有损）
        → 像素
```

统计过了：三个"要像真人"的脚本合计调用了 **718 次几何绘制原语、0 次读取参考图**。
`CONCEPT-ACTION-0-P0` 的爸爸的脸，实际上是两个 8 顶点多边形。

"像不像某个真人"的信息本体是像素级比例——眼距眼高比、鼻唇距、下颌角、发际线曲率。
这些量在自然语言里根本不可表达。所以这不是难度问题，是**信息量不够**：
目标像素里的比例信息在第二跳就丢光了，之后画多少轮都补不回来。

而且这个搜索**没有梯度、没有记忆**：
- 所有自动断言检查的是 alpha 二值、调色板封闭、SHA 双跑一致、头身比区间——**没有一条度量"像不像人"**；
- 每一轮都明令不复用上一轮的像素（`build_concept_model_0.py:9`、`CONCEPT-ACTION-0-P0/阶段说明.md:8`），从空画布重启。

所以十几轮不是在逼近，是在同一个分布里反复重采样。你感受到的"每轮都全 PASS 然后被我否掉"，
就是这个机制的直接表现。

**还有一个必须点破的地方**：`人物模型定档说明.md:32` 明令"禁止用矩形、椭圆和直线重新拼出
近似头像或身体"，而紧接其后的 `CONCEPT-ACTION-0-P0` 正是用 36 次 rectangle + 30 次 polygon
+ 13 次 disc 拼出来的。执行者不是不听话——**脚本不许读图，就只剩几何原语这一条路**。
合同要求了一个流水线在物理上无法交付的东西。

> ### 附带一个不太好听但重要的发现
>
> 最近这一轮（`CONCEPT-ACTION-0-P0`，Codex 亲自出手）相比 14 小时前被判为"失败稿"的
> `CONCEPT-1A`（Kimi），在七个维度上是**倒退**的：
> 姿态 18 张 → 6 张（丢掉攻击/受击/换气和全部右向）；有场景观感图 → 没有；
> 有水下青蓝配色映射 → 水下和水面共用一套肤色（违反规格书第 141 行）；
> 尺寸从合规的 66/78px → 爸爸 111px（超上限 32%，水下区只有 65px 高，根本放不下）；
> 连贯肢体 → 圆球串四肢；18 张匿名盲审 → 无盲审，且 Codex 同时是定档说明作者、
> 生成器作者和预审人，出题答题判卷三合一。
>
> **被判为失败的那一轮，其实是目前为止唯一能看见游戏样子的一轮。**

## 二、有一个取舍必须你来拍板，而且越早越好

这是整个项目从没有人正面回答过的问题：

**FC 原版的人物只有约 24 像素高。在 24 像素里，任何人都不可能像谁。**

去看 `过程文件/原版参考/官方截图/jp-action-h.gif`——原版的肩组是两个小圆团，没有五官。

所以"完全复刻原版画面"和"一眼认出是阳阳和爸爸"在像素层面是**物理冲突**的，
必须选一边。这就是你感觉"要么不像人、要么不像原版"的真正原因——
**这两个目标在当前设定下不可能同时达成，而没有人告诉过你要做选择。**

好消息是：**在规则层面它们完全不冲突**。"保留原版全部要素"真正指的是
规则、状态机、判定、节奏、构图、HUD、流程——这些 100% 可以复刻，而且现在几乎都没做。

我用同一条流水线把概念图渲染到了 5 个不同尺寸，请直接看图决定
（见 `决策图1_人物尺寸与辨识度.png` 与 `决策图2_三种尺寸放进场景.png`）：

| 人物身高 | 辨识度 | 与原版构图的距离 |
|---|---|---|
| 24px（原版尺寸） | 认不出，泳镜和眼镜都糊成一团 | 完全一致 |
| 32px | 勉强能认 | 很近 |
| **40px（推荐）** | **泳帽、泳镜、眼镜、笑容都清楚** | **人物略大，泳池仍是泳池，两人有充分活动空间** |
| 48px | 更清楚 | 开始显大 |
| 66px（概念路线现值） | 很清楚 | 两人占满水下区，打不开——水下区只有 64px 高 |

**我的建议：40px（阳阳）/ 47px（爸爸）。**

这不是估算，我已经把 40px 的成品精灵贴进**真实的、未经改动的游戏背景**验证过了
（从 HTML 里把 `BG_RLE` / `POOL_RLE` 直接解出来渲染，见 `真实场景_40px人物_3x.png`）：

| | 阳阳 | 爸爸 | FC 原版 |
|---|---|---|---|
| 水下横游精灵 | 59×26 | 61×32 | 39×21 |
| 相对 FC 倍数 | 高 1.24× / 宽 1.51× | 高 1.52× / 宽 1.56× | — |
| 占水下池体带（64px 高） | 41% | 50% | 33% |
| 两人并排总宽 | 120px = 屏宽 47% | | 78px = 30% |

**结论：40px 方案下，画布不用改、背景一个像素都不用重画。**

这一点非常重要，因为背景是**逐像素烘焙的 RLE 数据**（`BG_RLE` 73 行 + `POOL_RLE` 94 行
= 42,752 像素、8,640 个 run，来自实机帧量化）。概念路线草案第 5 节要求改成 512×448，
而那样做只有三条路，每条都很糟：

- 背景数据不动、绘制 ×2：背景每像素变 2×2 块，人物是 1×1——同屏两套像素网格，
  中央泳道绳、池底透视线、水面波纹全部变粗，斜线出现阶梯。清晰的人贴在糊掉的背景上。
- 真重画 512×448 背景：171,008 像素，是现有数据的 4 倍，**而且 FC 主机只输出 256×224，
  世界上不存在 512×448 的原版帧**——这份背景无法测量，只能靠人手重新解释，
  同时废掉"以日版官方截图为准"和整套像素差异图验收方法。
- 改场景几何：透视已经烘焙进像素里，改几何等于重画，回到上一条。

而 40px 让这三条路一条都不用走。附带保住的还有：代码里 386 个坐标字面量、HUD 布局、
Oxy 槽 63px 宽、以及全部已标定的玩法数值（`swimSpeedFp` 等都是按 21–42px 人物标的，
人物放大 4 倍后同样的速度会像慢动作）。

拍板后，请把这个数字写进一个**唯一的**尺寸合同，并把规格书里所有 24×24 头像的条款、
以及概念路线草案里 60–84px 和 512×448 的条款，**明确标注作废**。
现在这两套规则同时有效，是很多返工的直接来源。

## 三、美术：换方法，不换人

### 3.1 核心改动只有一句话

**把概念图从"仅供人工观察的参考"改为"构建输入"。**

隐私诉求（"本地勿提交"）和"不作为构建输入"是**两件不同的事**，现在被混为一谈了。
图片留在本地 + 写进 `.gitignore` + 不上传，完全可以满足隐私要求，
同时让脚本读取它的像素。

### 3.2 已经验证可行

我用 40 行图像处理代码跑通了完整流水线，产物在 `sprites/` 与 `审核板-本地勿提交.png`：

```
概念图（1738×905，唯一母版）
  → 自动探测 8 个姿态格子并紧致裁切
  → 曼哈顿距离阈值抠主体
  → RGB 与 alpha 分开降采样：
       RGB  用 BOX 块平均  → 抹掉 AI 生图的抗锯齿和噪点
       alpha 用覆盖率 ≥50% 二值化 → 干净硬边，无半透明
  → 两角色共享调色板量化（24 色，无抖动）
  → 透明 PNG + manifest（含锚点、尺寸、哈希）
```

结果：8 张精灵，alpha 严格二值，调色板封闭，双跑哈希一致——
**它通过了旧脚本的全部机器门，但人物是真的像。**

关键工艺有两处值得强调，Kimi 容易做错：

1. **RGB 和 alpha 必须分开降采样。** 直接缩放 RGBA 会把背景灰混进边缘，产生脏边。
2. **同一角色的所有姿态必须共用一个缩放因子**（用直立的 jump 姿态定标）。
   逐张各自缩放到"看起来差不多大"，是跨动作比例漂移的根源，也就是
   "换个动作就不像同一个人"的几何成因。

脚本已经写好：`build_sprites_from_concept.py`，可直接交给 Kimi 接手扩展。

### 3.3 还缺的 90% 动作怎么办

需求盘点：约 32 个动作帧 × 2 角色 × 2 朝向 ≈ **96–128 张**。概念图只有 8 张。

三个手段按优先级组合使用：

**① 镜像（免费，已验证）**
左右翻转的质量完全干净，identity 无损。直接砍掉一半工作量。
唯一注意：泳镜/眼镜的高光锚点需要在镜像后按左上光源重画（CONCEPT-1A 已经做对了这件事，
它的 hi 锚点机制值得保留）。

**② 部件化拼装 —— 但必须在高分辨率上做**

我测过了：**在 40px 的成品精灵上旋转手臂，会直接崩**——出现空洞、断线、锯齿。
所以"cut-out rig"在像素画上的朴素做法是不成立的。

但换个顺序就完全可行：**在 1738px 的概念图原始分辨率上切部件、旋转、拼姿态，
最后才降采样。** 我验证过 15°/30°/45°/60° 四个角度，降采样后全部是干净的像素画，
轮廓连续、无空洞（见 `B路线修复_高分旋转后降采样.png`）。

这条路线的真正价值在于：**头部是同一份源像素，每一帧都一样。**
"动作变了人就不像了"从此在原理上不可能发生。

**③ 补画概念图**

骑头、肩组、拉脚、气绝、败北这些姿态，靠部件拼装拼不出来，需要新的概念图。
用生成第一张概念图的**同一个图像模型**、同一套提示词锁住特征（蓝泳帽+白框泳镜+蓝泳装 /
短黑碎发+黑粗框眼镜+深色泳装+成年体型），按 FC 原版的姿势补画，再走同一条流水线。

**生成一张新概念图，比让 AI 用代码手绘一个角色，便宜一个数量级、质量高两个数量级。**

### 3.4 旧的验收硬门：保留什么、废弃什么

| 现有硬门 | 处置 | 理由 |
|---|---|---|
| alpha 严格二值 | **保留** | 新流水线天然满足 |
| 调色板封闭 + 双跑哈希一致 | **保留** | 确定性有价值，新流水线天然满足 |
| 尺寸/头身比区间 | **保留但只留一套** | 现在有三套互相矛盾的，必须裁决 |
| "人体母版 → 身份 mask → mask 外 RGBA 差异为 0" | **整套废弃** | 这是"FC 轮廓约束下逐像素换色"的补救工艺。新路线下人物直接来自概念图，不存在"母版"和"身份层"的分离，这套门无对象可依 |
| 轮廓 XOR ≤10% vs 原版 | **废弃** | 已经决定不逐像素复刻原版人物了，留着只会自相矛盾 |
| "主 HTML SHA 未变 = PASS" | **立即废弃** | 这是让项目停摆 6 天的直接原因 |

## 四、代码：立刻拆成两条互不阻塞的轨

现在的结构是单文件 1414 行，人物精灵是手敲的 24×24 ASCII 字符网格常量
（`const AVATAR = {...}`，第 443 行），`drawPart()` 逐像素 `fillRect` 上屏。
问题不在于单文件——单文件是对的，符合"双击就能玩"的要求——
问题在于**美术数据和玩法代码焊死在一起**，所以美术不定稿，玩法就动不了。

### 4.1 资产层解耦（半个工作时段，立刻做）

把人物精灵抽成一个数据契约，玩法代码只认契约，不认具体是谁画的：

```js
const SPRITES = {
  meta:    { palette:[...], yyHeight:40, ddHeight:47 },
  frames: {
    "yy.UW.0":   { w, h, anchorX, anchorY, data },   // data 可以是字符网格，也可以是 base64 PNG
    "yy.KICK.1": { w, h, anchorX, anchorY, data,
                   hitbox:[{x,y,w,h}], hurtbox:[...] },
    ...
  }
};
```

配一个**占位精灵生成器**：在正式美术到位前，用当前 24×40 的老精灵（或纯色块 + 标注）
按同样的契约填满全部 32 个动作。占位和正式资产走同一个 manifest 字段，
换美术时**玩法代码零改动**——这是"两条轨并行"能成立的技术前提。

单 HTML 约束的处理：写一个 `bake.py`，把 `sprites/` 目录下的 PNG 转成 base64 或字符网格，
注入 HTML 的资产段。生成物是单文件，开发时是分离的。

### 4.2 战斗内核（规格书 3.1 的要求，约 2 个工作时段）

这一段是整个项目技术上最容易做错、返工代价最高的地方，值得一次做对：

```js
function tick() {
  const snap = { yy: freeze(yy), dad: freeze(dad) };   // ① 同一份旧状态快照
  const inYY  = inputSource.yy.read();                 //    双方输入同时冻结
  const inDad = inputSource.dad.read();                //    1P/2P/CPU/REPLAY 统一抽象

  const intentYY  = decide(snap.yy,  inYY,  snap.dad); // ② 各自生成意图，只读快照
  const intentDad = decide(snap.dad, inDad, snap.yy);

  const events = resolve(snap, intentYY, intentDad);   // ③ 统一解析碰撞/命中/抓取/优先级

  commit(yy, dad, events);                             // ④ 同时提交
}
```

成对交互（肩组 / 骑头 / 拉脚）用**唯一一个 interaction 对象**驱动，两个角色都只持有它的 id：

```js
interaction = {
  id, kind:'GRAPPLE'|'MOUNT'|'LEGPULL',
  phase, pairTick,
  aId, bId, aRole:'attacker', bRole:'victim',
  pairAnchor:{x,y}, facing, drawOrder,
  appliedEvents: Set()          // (interactionId, eventId) 去重
}
```

这样做的收益很实在：不会有先手偏差、不会穿插、不会永久锁死，
而且固定输入流能复现出完全相同的逐 tick 状态 hash。

**判定盒必须是独立数据**，不能用透明像素外接框代替。跳跃骑乘要用
"上一 tick 到下一 tick 的向下扫掠 + 水平重叠 + 目标可骑状态"三者共同判定，
只检测当前是否相交会漏掉高速穿透。

## 五、新的阶段表

**两条硬规则：**
1. **每个阶段结束时，游戏必须是可以玩的、并且和上个阶段明显不一样。** 只产出静态 PNG 的阶段一律不批。
2. **每个阶段的验收标准必须是有限、可判定的。** "用户觉得像不像"不是验收标准——
   把它前置成一次性的定稿会（见阶段 A1），定稿之后不再回头审。

| 阶段 | 轨 | 目标 | 产出 | 验收标准 | 量级 |
|---|---|---|---|---|---|
| **A0** | 合流 | 裁决尺寸与规则冲突 | 一份《唯一尺寸与画风合同》；旧条款标注作废 | 规格书 + 概念草案里的矛盾条款全部有明确裁决 | 1 小时 |
| **A1** | 美术 | 概念图流水线定稿 | 8 张 40px 精灵 + manifest + 审核板 | 你看一次审核板说"可以"。**通过后本轮不再返修** | 半个时段 |
| **B0** | 玩法 | 资产层解耦 + 占位精灵 | SPRITES 契约、bake.py、32 个动作的占位帧 | 游戏正常运行，人物换成占位帧 | 半个时段 |
| **B1** | 玩法 | HP / 倒计时 / 胜负 | HUD 活起来 | 时间真的在倒数，HP 能扣，扣到 0 出胜负 | 1 个时段 |
| **B2** | 玩法 | 同步战斗内核 + 踢击 | 双人快照结算、interaction 骨架、踢击全相位 | 两人能互相踢中并掉血；固定输入回放 hash 一致 | 2 个时段 |

### 关于规格书第 7 节的标定标准

现行要求是：`ORIGINAL_TUNING` 每个值都要从 60Hz 逐帧录像测量至少 3 次、误差 ≤1 tick。
40 个键里现在只有 `diveTicks` 一项是实测。

**这个标准对一个给孩子做的家庭游戏是不成比例的**——它本身是一个考古研究项目的工作量，
而且你手上只有 30fps 编码的录像，物理上无法宣称 1 tick 精度。

建议降级为两档：
- **硬标准（保留）**：比赛 3:00、HUD 结构与布局、状态机拓扑、操作映射、
  "氧气归零进入气绝并持续掉血"这类**规则性**事实——这些才是"原版要素"。
- **软标准（改为"合理即可，以试玩手感为准"）**：具体的帧数、速度、伤害、击退、硬直。
  写进 `ORIGINAL_TUNING` 并标 `估值`，先让游戏跑起来，再和阳阳一起玩着调。

**手感是调出来的，不是测出来的。**

## 六、怎么指挥 Codex 和 Kimi

现在的分工出了问题：Codex 既写规则、又写生成器、又当预审人，
在 `CONCEPT-ACTION-0-P0` 里出题答题判卷三合一。而 Kimi 被要求做一件它做不到的事
（用代码手绘像真人的角色），于是只能不断交出"机器全 PASS 但视觉不通过"的东西。

### 重新分工

- **Kimi = 执行**。写玩法代码、写图像处理流水线。它擅长这个。
  **不要再让它"画"人物**——让它写"处理概念图的脚本"。
- **Codex = 审查代码与规则一致性**。审 diff、审契约、审确定性。
  **不要让它同时产出美术**——它产出的东西不能由它自己预审。
- **你 = 唯一的视觉裁判，而且只在定稿会上裁一次**。
  美术定稿后进入冻结，后续阶段不再重开视觉评审。

### 三条止损信号（出现任何一条就停下来）

1. **某一轮的产出没有进入游戏**——立刻停。产物不进游戏的阶段一律不批。
2. **验收记录里出现新的禁令**——立刻停。规则只能改总法，不能写在验收附注里。
   现在至少有 60 条新禁令散落在验收记录中，规格书本身却完全没提过"概念画风"。
3. **同一个东西被推翻重做第二次**——立刻停，改成"在上一轮基础上修补"。
   十几轮全部从空画布重启，是累积为零的根本原因。

### 仓库该收拾一下

`main`、`fc-replica`、`concept-style-game` 三个分支现在指向**同一个 commit**，
所有概念工作都没有提交。建议：

```bash
git add 过程文件/ 输出/ && git commit -m "concept-fork: 存档 R3B/CONCEPT 各轮过程文件"
```

把过程存档提交到 `concept-style-game`，让分支名和实际内容对上。
新流水线的产物目录（含家庭外貌特征）记得加进 `.gitignore`。
