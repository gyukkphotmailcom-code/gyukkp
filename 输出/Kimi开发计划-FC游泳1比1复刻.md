# Kimi 开发计划：FC《热血新纪录》游泳大乱斗 1:1 复刻

版本：2026-08-26（2026-08-27 范围调整）
执行人：Kimi
当前目标：先完成一个可独立游玩的“日版 FC 原版游泳层”，包括玩法、原版人物、完整动作、
HUD、音乐音效、开场和结算；验收通过后，再把原版人物替换成阳阳/爸爸，玩法代码不再改动。

**范围调整（2026-08-27，用户裁决）**：

- 最终模式只有**本地双人 1v1（人对人，同键盘）**：1P=WASD+F/G，2P=方向键+K/L，Enter/R 重开；
- **不开发 AI/CPU 对手**，相关代码、参数和验收已全部删除；此前所有 CPU 对局结论不再适用；
- 固定输入 REPLAY 只用于自动验收（verify.js 的确定性回放），**不是玩家模式**；
- 当前重点不变：原版玩法、动作、人物和音乐复刻。

本项目的“完整复刻”范围是**游泳大乱斗项目本身**，不是同时重做其他四项比赛。游泳专属道具、
选手属性和会影响游泳的赛前选择属于范围内；其他比赛和完整商店街剧情不属于本阶段。

## 一、先纠正当前方向

当前版本不能继续按“已有状态机基本正确，只补图片”的思路开发。任天堂官方说明书明确写的是：

- 水面按 A 跳跃；
- 左右方向键只在跳跃前改变跳跃方向；
- 水面按住 ↓ 下潜；
- 只有水下才允许方向键自由移动。

因此当前 `ST.SURF` 中 `c.axFp +=/-= surfDriftFp` 是明确错误，必须删除。水面角色的 x 坐标
不能通过按住左右平移，只能通过跳跃的水平位移改变。第一项验收必须是：水面按住左右 10 秒，
人物 x 坐标保持完全不变；随后按 A，人物才按预选方向跳跃。

当前人物动作也不是“暂时不好看”，而是状态表达不完整：正式家庭人物帧只有 20 个，另有 124 个
借用占位帧；`GRAPPLE_STRUGGLE`、`MOUNTED`、`DROWN`、`LOSE` 等状态仍借用不相干姿态，
受击、受身、挣扎和气绝神态不能被玩家识别。玩法复刻阶段不得再把这些占位帧算作完成。

## 二、视频对照后的当前差距清单

以下不只包含“看起来不像”，还包含当前源码中已明确标成估值或占位的实现。

| 项目 | 原版视频/说明表现 | 当前版本 | 判断 |
|---|---|---|---|
| 母版 | 日版人物、姓名、属性、音乐和 HUD 是一套完整系统 | 日版背景、日版国夫属性、美版 Todd 属性、家庭人物混用 | 明确不应继续混用 |
| 开场 | 选手站在起跳台，出现 RACE/GET READY，俯身后统一起跳入水 | 重开后两人直接出生在水面 | 明确缺失 |
| 水面方向键 | 左右只预选下一次跳跃方向 | 左右会以 `surfDriftFp` 持续平移 | 明确错误 |
| 跳跃 | 有原版起跳、腾空、下落、入水帧和固定轨迹 | 50 tick 抛物线及位移都是无录像证据的估值 | 未复刻 |
| 超级换气 | 完整抬身、张嘴、手臂和落水动画，Oxy 按原版节奏变化 | 4/12/18/10 四段和结束回满均是残缺样本推测 | 未复刻 |
| 水下 A 连打 | 官方只确认“移动中连打 A 提速” | 自创 `boostFp` 储能、上限和缓慢衰减模型 | 规则外形相似，算法无证据 |
| 水下待机/转向 | 视频中姿态随方向和动作切换 | 无输入默认头朝下 `UWD`，转向没有独立过程 | 高概率错误 |
| 踢击 | 独立起手、命中、被打翻转/蜷缩、受身恢复 | 6/6/10 tick 为估值，被打仅通用两帧+直线击退 | 未复刻 |
| 肩组 | 两人合拢、对峙、出拳、被打后仰/挣扎、分离是成对动画 | 基本按键规则已修正，但节奏、伤害、表情、层级和解除均为估值/占位 | 仅规则骨架成立 |
| 骑乘 | 跳落头顶、骑手压制、被骑者明显挣扎，向下潜水脱身 | 被骑帧借用无关动作；另加了 20 tick `escapeFp` 进度 | 表现缺失，数值无证据 |
| 拉脚 | 伸手、抓脚、被抓者惊吓翻转、两人同步下沉、释放 | 范围、抓取8 tick、拖拽24 tick全是估值，仅两张占位姿态 | 未复刻 |
| 气绝 | Oxy=0 后有明确眩晕/无力神态、暂时失控、HP下降及恢复/败北分支 | `DROWN` 两个占位帧、自动上浮、部分回氧和掉血速度均为估值 | 未复刻 |
| 人物表情 | 呼吸、攻击、疼痛、挣扎、恐慌、眩晕、KO 都有不同脸部/身体状态 | 大量状态共用正常脸和不相干身体 | 明确缺失 |
| 人物动作资产 | 原版每种交互都有可识别的专用帧 | 正式家庭帧20个，借用 placeholder 124个 | 远未完成 |
| 奖牌 | 数量、出现时机、上浮轨迹、价值和音效受原版逻辑控制 | 固定约4秒生成一枚，速度/漂移为估值，无拾取音效 | 只有示意实现 |
| 游泳道具 | 食人鱼、氧气口香糖、脚蹼等会改变游泳过程 | 未实现 | 缺失 |
| 角色属性 | 同一日版角色表中的 HP/速度/力量/防御共同参与 | 阳阳用日版国夫，爸爸用美版 Todd 映射 | 不适合作为1:1基准 |
| CPU | 原版有 CPU 对手 | 项目已改为只做本地双人 1v1，不开发 AI（2026-08-27 用户裁决） | 不再适用 |
| 比赛节奏 | 由原版各个基础参数自然产生 | 曾为了让 CPU 局达到22秒而反向调伤害/气绝速度（CPU 已取消，此教训仍适用于双人局长） | 校准方法不对，应量基础参数 |
| 结算 | 原版 WINNER、败者动作、赛次/晋级演出 | 自制黑框 `YANGYANG WIN / DAD WIN` | 明确不一致 |
| 音乐音效 | 有游泳 BGM、GET READY、入水、换气、拳脚、奖牌、气绝、胜负音效 | 完全没有音频系统 | 明确缺失 |
| 时钟 | NTSC 原始运行频率约60.0988Hz，原版计时按游戏帧推进 | `STEP=1000/60`、时间也直接除60 | 尚未对齐 |
| 可视比例 | 原版人物约24px级，动作接触距离与此一致 | 家庭人物40–60px，正式版判定盒覆盖率明显偏低 | 会反向污染玩法手感 |

泳池透视、远景、水面/水下分区和 HUD 大框架是当前最接近原版的部分，可以保留为视觉基底；
但文字、选手名、原版人物头像、音乐和事件演出仍需按日版统一重做。

## 五、必须完整覆盖的原版动作集

### A. 比赛流程

1. 起跳台待机；
2. 选手登台/亮相；
3. `RACE / GET READY`；
4. 向前俯身准备；
5. 从台上起跳、水平飞行、头朝下入水；
6. 开始计时；
7. HP=0 或时间到结算；
8. 败者姿态、`WINNER`、奖牌/下一场过渡。

### B. 水面动作

1. 水面漂浮待机；
2. 左右预选跳跃方向：只更新方向，不产生 x 位移；
3. A 跳跃：起跳准备、离水、腾空、下降、入水/回到水面；
4. 跳到对手头上的骑乘分支；
5. 按住 ↓ 的下潜准备、翻身、入水；
6. B 超级换气：抬身、张嘴吸气、手臂动作、落回水面；
7. 被拉脚时的惊吓、失衡、被拖入水下；
8. 被骑时的挣扎循环和下潜脱身；
9. 从水下上浮、露头、回到漂浮状态；
10. 气绝后浮回水面的喘息/恢复状态。

### C. 水下移动

1. 水平左/右游泳循环；
2. 向上游、向下游；
3. 斜向移动；
4. 移动中连打 A 的加速循环；
5. 停止输入时的水下待机姿态；
6. 转向过程；
7. 到达水面边界后的上浮过渡；
8. 到达池底/左右边界时的限制。

当前代码把“无输入”直接归为头朝下的 `UWD`，这也必须以视频重新核对，不能默认保留。

### D. 水下攻击与受身

1. B 踢击起手；
2. 踢击有效帧；
3. 踢击收招；
4. 踢空；
5. 踢中对手；
6. 被踢者的痛苦表情、身体折叠/翻转、击退；
7. 被踢后的受身/恢复动作；
8. 低 Oxy 时被踢进入气绝的分支；
9. 同 tick 双方攻击时的原版优先级。

`HIT` 不能再只用两个通用占位帧加直线击退。必须按原版拆出“命中瞬间—翻滚/蜷缩—减速—恢复控制”，
并确认受身期间是否能输入、是否无敌、是否会再次被击中。

### E. 肩组与挣扎

1. 水下朝对手方向移动并接触；
2. 双方进入肩组的合拢动作；
3. 肩组中立循环；
4. 任一方按 B 的出拳准备、命中、收拳；
5. 被打者的头部后仰、闭眼/痛苦嘴、身体挣扎；
6. 两人交替出拳时的层级、朝向和锚点；
7. 双方同时按 B 时的原版处理；
8. Oxy 归零、HP 归零或上浮需求导致的解除；
9. 解除后的双方受身/分离动作。

肩组不是“一个攻击动画叠在一个静止对象上”。两个人必须共用一套成对动画时间线；任何一方出拳，
另一方都要进入对应的受击/挣扎表情帧。禁止恢复固定攻击方/防守方和原创挣脱槽。

### F. 骑乘与拉脚

1. 跳跃落到对手头上的精确判定帧；
2. 骑手坐姿/压制循环；
3. 被骑者挣扎：脸部恐慌、手脚划动、水花；
4. 被骑者按住 ↓ 后的共同下潜；
5. 骑手掉落/分离、双方恢复；
6. 水面敌人下方 ↑+B 的拉脚起手；
7. 手接触脚的命中帧；
8. 水面角色惊吓和翻转；
9. 两人同步下沉；
10. 释放及各自恢复控制。

### G. Oxy、气绝与败北神态

1. 正常呼吸气泡；
2. 低 Oxy 的表情/动作变化（若原版存在）；
3. Oxy=0 的命中瞬间；
4. 眼睛闭合/眩晕、嘴部、无力身体姿态；
5. 暂时失控和 HP 缓慢下降；
6. 自动上浮/下沉轨迹；
7. 回到水面后的喘息与恢复；
8. HP=0 的最终败北姿态；
9. 时间到判负时的原版姿态。

表情是动作状态的一部分，不是最后统一换头像。至少要建立 `NEUTRAL / INHALE / ATTACK / PAIN /
STRUGGLE / PANIC / DIZZY / KO` 八类头部或整身帧槽；具体是否合并，以原版逐帧证据为准。

## 六、阶段 1：重做玩法状态机，只使用调试人物

不要直接在现有 `ST` 上不断打补丁。先根据动作矩阵画出状态转换图，再实现最小状态集合。建议拆成：

- `PRE_RACE_*`
- `SURFACE_IDLE / SURFACE_JUMP / SURFACE_DIVE / SURFACE_BREATH / EMERGE`
- `UW_IDLE / UW_SWIM / UW_BOOST / UW_KICK / UW_HIT / UW_RECOVER`
- `GRAPPLE_ENTER / GRAPPLE_HOLD / GRAPPLE_PUNCH / GRAPPLE_HIT / GRAPPLE_BREAK`
- `MOUNT_ENTER / MOUNT_RIDE / MOUNTED_STRUGGLE / MOUNT_DIVE_ESCAPE / MOUNT_BREAK`
- `LEGPULL_REACH / LEGPULL_GRAB / LEGPULL_DRAG / LEGPULL_RELEASE`
- `DIZZY / DIZZY_SURFACE_RECOVER / KO / RESULT`

状态名可以调整，但不能再用一个 `HIT` 或 `DROWN` 同时承担多种视觉和控制语义。

这一阶段只使用 24px 左右的原版比例调试人物/轮廓帧。暂时禁用家庭人物 bake，避免 40–60px 大人物
改变碰撞距离。所有坐标、锚点、速度、hitbox/hurtbox 先按原版画面标定。

## 七、阶段 2：动作帧与判定逐项落地

按以下顺序做，每完成一项就加入自动验收：

1. 水面锁位、方向预选、跳跃；
2. 下潜、上浮、超级换气；
3. 水下八方向移动、转向、A 连打加速；
4. 踢击、被踢、受身；
5. 肩组进入、双方出拳、被打挣扎、解除；
6. 骑乘、被骑挣扎、按 ↓ 脱身；
7. 拉脚全套成对动作；
8. Oxy=0、气绝、恢复、KO；
9. 起跳台、GET READY、结果演出；
10. 奖牌、气泡、水花和音效事件。

每个动作的动画定义必须包含：帧 ID、持续 tick、锚点、可控性、速度、hitbox、hurtbox、声音事件、
HP/Oxy 事件。不能把时长散落在多个 `if (t > N)` 里。

## 八、阶段 3：完成日版原版层

状态机和动作轨迹稳定后，先完成原版层，不进入家庭人物建模：

1. 选定日版 FC 为唯一母版，删除日版/美版角色属性混用；
2. 按日版原始比例完成本项目所用选手的完整人物帧、配色、姓名和属性；
3. 所有可达动作均使用原版专用帧，`placeholder:true` 数量必须为 0；
4. 加入原版游泳 BGM、GET READY、跳水、游动、换气、踢击、拳击、拉脚、骑乘、奖牌、
   气绝、KO 和 WINNER 音效；
5. 音效触发写进动作帧事件，不能依赖渲染帧碰巧播放；
6. 完成起跳台、开场文字、原版 HUD 文案、胜负和赛次过渡；
7. 实现会影响游泳的原版道具和角色属性；
8. ~~CPU 行为建模~~（2026-08-27 范围调整：项目只做本地双人 1v1，不开发 AI；本条删除。基础参数标定仍不得以“最终打了多少秒”反向调整）；
9. 输出一份完全不含阳阳/爸爸元素、可以单独玩的“日版原版游泳复刻版”。

音乐技术上优先使用 Web Audio 的事件化播放器。若使用录制音轨，必须验证循环点、动作音效叠加、
暂停/重开和后台恢复；不能只有一段与玩法脱节的 MP3 循环。

## 九、阶段 4：1:1 验收门

Kimi 必须扩充 `verify.js`，以下均为阻塞项：

1. 水面按住左右 600 tick，x 位移必须为 0；
2. 左/右预选后按 A，跳跃落点、最高点和时长与原版样本一致；
3. 下潜、上浮、换气的帧序列和 Oxy 变化顺序一致；
4. 同一输入流下，水下普通游速和 A 连打游速可复现；
5. 踢击仅在原版有效帧命中一次；
6. 被踢者必须经过独立 `UW_HIT → UW_RECOVER`，表情和身体帧均非占位；
7. 肩组双方均能出拳，双方都有独立痛苦/挣扎帧；
8. 被骑者必须有可见挣扎循环，按住 ↓ 才能走原版脱身路径；
9. 拉脚双方共用 interaction，位置同 tick 原子更新；
10. Oxy=0 后控制锁定、HP 下降、恢复/KO 路径与原版一致；
11. 任何可达状态都不能引用 `placeholder:true` 帧；
12. 左右镜像的锚点、hurtbox、hitbox 完全对称；
13. 固定输入录像双跑 hash 完全相同；
14. 浏览器后台恢复后不能补算出多次攻击或跳过动画事件；
15. 60.0988Hz 输入记录回放时，关键检查点位置误差目标为 0 tick/0px；受 30fps 视频限制的样本
    可暂收至 ±1 个视频帧，但必须标成“录像估测”，不能宣称精确复刻。

另做一个 `?debug=1` 模式，可显示当前状态、tick、锚点、速度、hitbox/hurtbox、HP/Oxy 和 interaction ID。
调试层不能改变玩法 hash。

## 十、阶段 5：阳阳/爸爸建模与换皮

只有日版原版层完成且阶段 4 全绿后，才开始阳阳/爸爸建模。替换原则：

1. 状态数、帧时长、锚点轨迹、判定盒完全不变；
2. 家庭人物每个原版动作槽必须有对应帧，不能借其他动作占位；
3. 受击、受身、挣扎、恐慌、气绝、KO 的眼睛和嘴必须逐状态绘制；
4. 若大人物视觉尺寸导致频繁“看着碰到但没命中”，调整绘画留白或内部锚点，不能扩大玩法判定；
5. 阳阳和爸爸可有体型差，但二者动作语义和接触点必须与同一套原版骨架一致。

## 十一、HTML 技术评估

### 结论

HTML5 可以支持这个项目。256×224 的像素 Canvas、约 60Hz 固定步进、两名角色、成对交互、
百余帧精灵和 FC 级音效，对浏览器性能都很轻。没有必要因为玩法复杂度改成 Unity。

但“单个巨大 HTML 手写所有内容”不适合继续开发。建议开发期模块化，交付时再打包成单 HTML：

```text
src/
  game-clock.js       固定 60.0988138974405Hz 步进
  input.js            键盘/手柄输入和回放
  state-machine.js    单人状态
  interactions.js    肩组/骑乘/拉脚成对状态
  physics.js          位移、边界、碰撞
  animation.js        动作矩阵和帧事件
  render.js           256×224 Canvas 像素渲染
  audio.js            Web Audio
  data/actions.js     帧、tick、锚点、判定盒
  data/tuning.js      已标定参数和证据来源
```

构建脚本再合成为 `阳阳水泳大乱斗-原版复刻.html`；`阳阳水泳大乱斗-本地美术勿提交.html` 仍应是生成物，
不能直接在生成物上长期修改。

### HTML 需要特别处理的限制

- `requestAnimationFrame` 不是稳定的 FC 时钟，显示器也可能是 120/144Hz；必须使用固定步进累加器，
  逻辑频率设为 60.0988138974405Hz，渲染不能反过来决定逻辑 tick。
- 标签页进入后台会被限速；恢复时要限制最大补帧数，不能一口气结算几百次攻击。
- Web Audio 首次播放需要用户手势解锁；音效资源应内嵌或统一预载。
- `file://` 下外部资源加载有兼容问题；最终单 HTML 应内嵌精灵和音频，开发期可使用本地服务器。
- CSS 必须 `image-rendering: pixelated`，Canvas 逻辑分辨率固定 256×224，优先整数倍缩放。
- 键盘两人同时按键可能受硬件鬼键影响；2P 最终应支持 Gamepad API。
- 若目标升级为“NES CPU/PPU/APU 周期级完全一致”，那实际是在写模拟器，普通 Canvas 复刻不够；
  但对本项目要求的画面、输入、动作、碰撞、数值和节奏 1:1，HTML 完全够用。
