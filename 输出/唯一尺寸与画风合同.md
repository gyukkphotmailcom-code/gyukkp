## 二、尺寸合同（唯一有效）

```
阳阳直立身高 = 40 px
爸爸直立身高 = 47 px        （= 40 × 1.18，比例取自概念图实测）
```

- **定标姿态**：直立的 `jump` 姿态。同一角色的**所有**姿态共用**同一个缩放因子**。
- **禁止**逐张缩放到"看起来差不多大"——这是跨动作比例漂移、"换个动作就不像同一个人"的几何成因。
- 其余姿态的画布尺寸由流水线按该缩放因子自动得出，**不单独规定**，但必须满足第三节的硬约束。

### 已验证的实际产出（`build_sprites_from_concept.py --target-height 40`）

| 姿态 | 阳阳 | 爸爸 |
|---|---|---|
| surf（水面） | 61×32 | 60×39 |
| jump（跳跃） | 37×40 | 41×47 |
| uw（水下横游） | 59×26 | 61×32 |
| emerge（出水） | 53×38 | 55×46 |

### 画布与场景：一个像素都不改

```
逻辑画布      256 × 224        不变
比赛区        y = 0..167       不变
远景          y = 0..71        不变（BG_RLE，73 行，实机帧量化，不重画）
透视水面      y = 72..101      不变
水下池体      y = 102..165     不变（POOL_RLE，94 行，实机帧量化，不重画）
分隔线        y = 166..167     不变
HUD           y = 168..223     不变
CSS 缩放      整数倍 1..3      不变
```

**`概念画风版开发路线草案.md` 第 5 节要求的 512×448 —— 作废。** 理由：

1. 背景数据不动、绘制 ×2 → 背景每像素变 2×2 块而人物是 1×1，同屏两套像素网格，泳道绳/透视线/波纹全部变粗，清晰的人贴在糊掉的背景上。
2. 真重画 512×448 → 171,008 像素（现有 4 倍），而且 **FC 主机只输出 256×224，世界上不存在 512×448 的原版帧**，这份背景无法测量，同时废掉"以日版官方截图为准"和整套像素差异图验收方法。
3. 改场景几何 → 透视已烘焙进像素，等于重画，回到第 2 条。

40px 方案让这三条路一条都不用走，并附带保住：代码里全部坐标字面量、HUD 布局、Oxy 槽 63px 宽、以及所有已标定的玩法数值（`swimSpeedFp` 等按 21–42px 人物标定，人物放大 4 倍后同样速度会像慢动作）。

## 三、硬约束（可机器判定，违反即 FAIL）

| # | 约束 | 判定方式 |
|---|---|---|
| H1 | 阳阳定标身高 = 40px，爸爸 = 47px | manifest `targetHeight` |
| H2 | 同一角色所有姿态共用一个缩放因子 | manifest `scale` 每角色只有一个值 |
| H3 | 任何姿态的精灵高度 ≤ 64px（水下池体带高度） | 逐帧检查 `h` |
| H4 | 两人并排总宽 ≤ 154px（屏宽 60%） | 最宽两帧宽度之和 |
| H5 | alpha 严格二值（只有 0 和 255） | 逐像素 |
| H6 | 调色板封闭：≤24 色，两角色**共用同一张** | 逐像素 ∈ palette |
| H7 | 双跑哈希一致（确定性） | 重跑比对 sha256 |
| H8 | 人物像素可反向追溯到概念图原像素 | 见第四节 |

H5/H6/H7 是**从旧流水线保留下来的**——新流水线天然满足，保留它们没有成本，且确定性有真实价值。

  "两张本地概念参考图仅供人工观察，不作为构建输入。" —— **作废**
- `build_concept_model_0.py:6`：
  "人物形象唯一来源：用户确认的两张本地概念参考图（仅人工观察，本脚本不读取）。" —— **作废**

> **隐私诉求与"不作为构建输入"是两件不同的事，此前被混为一谈。**
> 图片留在本地 + 写进 `.gitignore` + 不上传，已经完全满足隐私要求。
> 脚本读取它的像素与隐私无关。

### 4.2 唯一允许的生成路径

```
概念图（唯一母版，本地）
  → 探测姿态格子 + 紧致裁切
  → 阈值抠主体
  → RGB 与 alpha 分开降采样
       RGB  用 BOX 块平均       → 抹掉 AI 生图的抗锯齿与噪点
       alpha 用覆盖率 ≥50% 二值化 → 干净硬边，零半透明
  → 两角色共享调色板量化（24 色，无抖动）
  → 透明 PNG + manifest（尺寸、锚点、哈希）
```

参考实现：`过程文件/Claude重启规划/build_sprites_from_concept.py`（已跑通并验证）。

**两处最容易做错、必须照做的工艺：**

1. **RGB 和 alpha 必须分开降采样。** 直接缩放 RGBA 会把背景色混进边缘，产生脏边。
2. **同一角色所有姿态共用一个缩放因子。** 见 H2。

### 4.3 明令禁止

- ❌ 用 `rect` / `ellipse` / `polygon` / `disc` / 直线等几何原语绘制**任何人物像素**。
- ❌ 用自然语言形容词转写概念图，再由模型翻译成坐标（信息在这一跳全部丢失，不可收敛）。
- ❌ 逐张各自缩放到"看起来差不多大"。
- ❌ 把照片直接缩图或作为构建输入。

> 说明：`人物模型定档说明.md:32` 已经写过"禁止用矩形、椭圆和直线重新拼出近似头像或身体"，
> 但同时又规定脚本不许读图——**这份合同在物理上无法交付**，执行者只剩几何原语一条路。
> 本合同同时解除"不许读图"并保留"禁止几何原语"，两条现在是自洽的。

场景、HUD、粒子、字模**不受此限**，它们本来就是 RLE / 字符网格 / `fillRect`。

### 4.4 缺失动作的补齐顺序

约需 32 个动作 × 2 角色 × 2 朝向 ≈ 96–128 帧，概念图目前只有 8 张。按优先级：

1. **镜像**（免费，已验证 identity 无损）—— 直接砍掉一半工作量。唯一注意：泳镜/眼镜的高光锚点镜像后需按左上光源重画（`CONCEPT-1A` 的 hi 锚点机制做对了这件事，予以保留）。
2. **部件化拼装，且必须在概念图原始分辨率上做。** 在 40px 成品上旋转手臂会崩（空洞、断线、锯齿，已实测）。正确顺序是：在 1738px 原图上切部件 → 旋转 → 拼姿态 → **最后才降采样**。已验证 15°/30°/45°/60° 降采样后全部干净。此路线的核心价值：**头部是同一份源像素，每一帧都一样**——"动作变了人就不像了"从原理上不可能发生。
3. **补画概念图。** 骑头、肩组、拉脚、气绝、败北拼不出来，用生成第一张概念图的**同一个图像模型**、同一套特征提示词（蓝泳帽+白框泳镜+蓝泳装 / 短黑碎发+黑粗框眼镜+深色泳装+成年体型），按 FC 原版姿势补画，再走同一条流水线。

### 4.5 运行时资产结构

作废"24×24 完整头先贴上、16×16 身体填空"的机械拼接（此条与 `开发规格书.md:159` 一致，是强化不是变更）。

运行时的每一帧是**一张扁平的完整人物精灵**，通过 `SPRITES` 数据契约供给：

```js
SPRITES.frames["yy.UW.R.0"] = { w, h, anchorX, anchorY, rows, hurtbox, hitbox, placeholder }
```

玩法代码只认这个契约，不认像素是谁画的、来自占位还是正式美术。**换美术时玩法代码零改动。**

## 六、标定标准分级（替代规格书第 7 节的统一硬标准）

现行要求 `ORIGINAL_TUNING` 每个值都要从 60Hz 逐帧录像测量 ≥3 次、误差 ≤1 tick。
40 个键里只有 `diveTicks` 一项是实测。而手头只有 30fps 编码录像，**物理上无法宣称 1 tick 精度**。
这个标准本身是一个考古研究项目的工作量，对一个给孩子做的家庭游戏不成比例。降为两档：

**硬标准（保留，必须复刻）** —— 规则性事实：

- 比赛时长 3:00
- HUD 结构与布局（三行、条形槽、8×8 字模、1P/TIME/CPU 布置）
- 状态机拓扑与状态间的合法迁移
- 操作映射（方向 / A / B 各自的语义）
- "氧气归零进入气绝并持续掉血"
- HP 归零判负、时间到按 HP 判胜负

**软标准（改为"合理即可，以试玩手感为准"）** —— 具体数值：

- 帧数、速度、伤害、击退、硬直、粒子寿命

软标准写进 `ORIGINAL_TUNING` 并标注 `估值`，先让游戏跑起来，再和阳阳一起玩着调。

> **手感是调出来的，不是测出来的。**

  一次具名例外，不是对它的废除。
- **附带约束**：一旦将来拿到原版实机的肩组脱身数据，
  **以实机数据为准替换本机制**，本条自动失效。
- **失效日期**：2026-08-26。用户要求“玩法上一定要和原版对齐”后，已核到原版操作资料与
  实机攻略：肩组是双方连打 B 互相出拳，持续到一方被打沉；不存在固定攻击方/防守方、
  `escapeFp` 挣脱槽或无输入自动解开。因此本条按自己的“附带约束”自动失效，
  `开发规格书.md:491` 的“不能加入连打挣脱槽”恢复有效。

### A-2　连打挣脱的公平性问题移交 KID_ASSIST（随 A-1 失效）

- **背景**：连打挣脱使脱身快慢取决于按键速度，实测 2 次/秒以下必死、
  10 次/秒可在 1.1 秒脱身。成年人系统性快于幼儿（详见《建议台账》S-08 实测表）。
- **处理**：这属于 `开发规格书.md:384` 指定的 `KID_ASSIST` 层职责，**不在 ORIGINAL 层解决**。
  `ORIGINAL` 保持现有数值不变。
- **归属阶段**：B5（接入 2P / CPU 时一并建立 KID_ASSIST 参数层）。
- **状态**：2026-08-26 失效。ORIGINAL 已删除连打挣脱槽，不再需要对该原创机制做儿童辅助修正。
